# GoMobi (Mobi) API Reference

Entry point for GoMobi integration facts. Docs base: `https://gomobi.io/documents/<route>` (all facts checked 2026-10-21). GoMobi now trades as Mobi (Mobi Asia Sdn Bhd, formerly Mobiversa Sdn Bhd). Detail files:

- `gomobi-ewallets-qr.md`: Boost, GrabPay, ShopeePay, Touch 'n Go, DuitNow QR, 7-Eleven cash (EZYCASH).
- `gomobi-cards-payout.md`: card payment, saved card, payouts.
- `gomobi-codes.md`: bank codes, response codes, BIC codes, error lists.

## Integration Surfaces (Malaysia)

- Hosted Checkout (Mobi checkout page, one API call, HMAC-signed).
- FPX direct (B2C retail and B2B corporate) via HTML form post.
- Cards (Visa, Mastercard, UnionPay, 3DS) via HTML form post, plus saved-card charges by `walletId`.
- E-wallets: Boost, GrabPay, ShopeePay, Touch 'n Go.
- DuitNow QR.
- Cash over counter at 7-Eleven (EZYCASH).
- Payouts to bank accounts and DuitNow-registered e-wallets.
- Plugins: Shopify, WooCommerce, PrestaShop, OpenCart, Magento (see `account-setup.md`).

Default choice for a custom web checkout: Hosted Checkout, then settle from status/IPN where available. Use direct product APIs when the merchant needs a specific method UI (own bank list, QR on page, payouts).

## Credentials

All issued by Mobi during onboarding (see `account-setup.md`). Placeholders only:

- `<MOBI_API_KEY>`: mobiApiKey, also called motoApiKey or mobiKey. Used in bodies, headers, and as AES password for e-wallet/DuitNow/cash payloads.
- `<MOBI_LOGIN_ID>`: Merchant Login ID (`loginId`).
- `<MOBI_SECRET_KEY>`: mobiSecretKey, the 3DES key source.
- `<MOBI_SALT>`: AES-CBC PBKDF2 salt.
- `<MOBI_FPX_PARAM1>` / `<MOBI_FPX_PARAM2>`: FPX AES password and salt, sent by Mobi by email.
- `<MOBI_FPX_MID>` / `<MOBI_FPX_TID>`: FPX merchant and terminal id.
- `<MOBI_SUB_MID>`: sub-merchant id (`subMID`, `subMerchantMid`, `subMid`, `sub_mid`) when sub-accounts are used.
- `<MOBI_CHECKOUT_API_KEY>` / `<MOBI_CHECKOUT_API_SECRET>`: hosted checkout. The secret is generated by Mobi after production onboarding (`getsupport@gomobi.io`).

Never put any of these in frontend code.

## Authentication Algorithms

Docs: `authentication`, `authentication/aes-cbc`, `authentication/3des`. Every direct request uses encrypted payloads or signed values; the `Mobiapikey` header carries the API key (3DES-encrypted where stated).

### AES-CBC (payload encryption, checksums, IPN decryption)

| Item | Value |
|---|---|
| Algorithm | AES/CBC/PKCS5Padding (PKCS7, 128-bit block in Python) |
| Key derivation | PBKDF2WithHmacSHA256, password = mobiKey (or FPX `param1`), salt = salt (or FPX `param2`) as UTF-8, 65,536 iterations, 256-bit key |
| IV | 16 random bytes per message |
| Output | base64(IV + ciphertext) |

```text
encrypt(input, password, salt):
  iv  = random_bytes(16)
  key = PBKDF2_HMAC_SHA256(password_utf8, salt_utf8, 65536, 32)
  ct  = AES_256_CBC_encrypt(key, iv, PKCS7_pad(input_utf8))
  return base64(iv || ct)

decrypt(b64, password, salt):
  raw = base64_decode(b64)          # Cards: input is hex, convert hex -> base64 first
  iv, ct = raw[0:16], raw[16:]
  key = PBKDF2_HMAC_SHA256(password_utf8, salt_utf8, 65536, 32)
  return PKCS7_unpad(AES_256_CBC_decrypt(key, iv, ct))
```

Used for: FPX `checkSum` (param1/param2), Boost/Grab/Shopee/TNG `checkSum` (mobiKey/salt), DuitNow and cash `requestSignature`, and decrypting their `responseSignature` and IPN payloads.

Doc quirks:

- The Python FPX sample returns `encrypted_data.hex().upper()` when the input contains `#`; Java, PHP and C# return base64 only. Not explained in official docs (checked 2026-10-21).
- The "Cards" encrypt sample is different: AES/CBC/PKCS5Padding with a raw key string and an `initVector` string (no PBKDF2), base64 output, then a hex conversion helper. The cards page itself says card details are encrypted "RSA/PKCS1". Which key, IV and method apply to cards must be confirmed with Mobi.

### 3DES (mobiApiKey header, FPX POST IPN signature, payout IPN)

| Item | Value |
|---|---|
| Algorithm | DESede/ECB/PKCS5Padding |
| Key | first 24 bytes of mobiSecretKey (UTF-8) |
| Plaintext (header use) | mobiKey |
| Output | base64 |

```text
encrypt_api_key(mobiKey, mobiSecretKey):
  key = utf8(mobiSecretKey)[0:24]
  return base64(DES3_ECB_encrypt(key, PKCS5_pad(utf8(mobiKey), 8)))

decrypt(b64, key):
  return PKCS5_unpad(DES3_ECB_decrypt(utf8(key)[0:24], base64_decode(b64)))
```

PHP form: `openssl_encrypt($mobiKey, "des-ede3", substr($mobiSecretKey, 0, 24), OPENSSL_RAW_DATA)` then base64. The 3DES page table also lists "256-bit" and "65,536 iterations"; these do not apply to 3DES ECB and look copied from the AES table. The decrypt samples key on `mobiKey` (FPX) or a generic `key` (payout); confirm with Mobi which value decrypts your IPN.

## Hosted Checkout

Docs: `checkout/overview`, `checkout/malaysia`, `checkout/malaysia/authorization`, `checkout/malaysia/api`.

`POST /api/payment/v2/checkout/init`

Headers:

| Header | Required | Value |
|---|---|---|
| Content-Type | Yes | `application/json` |
| Authorization | Yes | `Bearer <base64 of MOBI_CHECKOUT_API_KEY>` |
| X-Signature | Yes | HMAC-SHA256 signature |
| X-Timestamp | Yes | Unix time in seconds |
| X-Nonce | Yes | random 32-char hex, unique per request |

Signature (order must not change):

```text
body_hash = SHA256(raw_request_body)
payload   = "POST" + "/api/payment/v2/checkout/init" + timestamp + nonce + body_hash
signature = base64(HMAC_SHA256(key = utf8(API_SECRET), data = payload))
```

The Java sample returns Base64 of the raw HMAC. Not documented in official docs (checked 2026-10-21): whether `body_hash` is hex or base64, and whether separators are used (none are shown). Sign the exact bytes you send. The FAQ says a Bearer token alone is accepted, but the signature is recommended for production.

Request body:

| Field | Type | Req | Notes |
|---|---|---|---|
| amount | Number | Yes | MYR, two decimals, e.g. `100.50` |
| currency | String | No | default `MYR` |
| order_id | String | Yes | unique |
| callback_url | String | Yes | HTTPS, customer redirect after success |
| redirect_url | String | No | cancel/error page |
| customer.name / email / phone | String | No | phone without `+60` |
| idempotency_key | String | No | dedup key |
| order_summary_enable | Boolean | No | enables `order_detail` |
| order_detail.orderDate | String | Yes* | ISO 8601 |
| order_detail.products[] | Array | Yes* | `productId`, `productName`, `quantity` > 0, `price` > 0, `total` = quantity x price |
| order_detail.subTotal / shippingFee / totalAmount | String | Yes* | `subTotal + shippingFee = amount` |
| sub_mid | String | No | sub-merchant |
| recurring | Boolean | No | recurring flag |

*Only when `order_summary_enable` is true; otherwise ignored.

Response: `checkout_url` (redirect customer), `session_id`, `expires_at` (epoch ms), `order_id`. Session lasts 10 minutes and is single use. Cancel sends the customer to `redirect_url`.

No checkout webhook or checkout status endpoint is documented (checked 2026-10-21). Ask Mobi how checkout payments are confirmed server-side before going live; do not fulfil from `callback_url` alone.

## FPX

Docs: `payin/malaysia/internet-banking/fpx` and its `get-available-banks`, `initiate-deposit`, `payment-response`, `ipn`, `status` pages.

Limits: B2C RM1.00 to RM30,000; B2B RM2.00 to RM1,000,000. Session expiry 15 minutes. No automatic refunds; refunds are manual through Mobi.

### Get available banks

`POST /api/fpx`, no headers, body `{"Service":"FULL_LIST"}`.

Response: `responseDataB2C.bankList[]`, `responseDataB2B.bankList[]`, `responseDataBT.bankTypeList[]` (`01` Retail, `02` Corporate). Bank fields: `BankCode`, `BankName`, `BankDisplayName`, `Logo`, `DDBankCode`, `LastUpdatedOn`, `Active` (`1` online, `0` offline). Cache it and refresh periodically; show offline banks as unavailable. Codes in `gomobi-codes.md`.

### Payment response (browser POST to redirectUrl)

Fields: `fpx_msgToken` (`01`/`02`), `fpx_fpxTxnId`, `fpx_sellerExOrderNo`, `fpx_fpxTxnTime`, `fpx_sellerTxnTime`, `fpx_sellerOrderNo`, `fpx_txnCurrency`, `fpx_txnAmount`, `fpx_buyerName`, `fpx_buyerBankId`, `fpx_buyerId`, `fpx_makerName`, `fpx_debitAuthCode`, `fpx_debitAuthCodeString`, `fpx_debitAuthNo`, `fpx_creditAuthCode`, `fpx_creditAuthCodeString`, `fpx_creditAuthNo`, `bankName`, `tid`, `mobiLink`, `redirectUrl`, `merchantName`, `date` (dd-MMM-yyyy), `time` (HH:mm:ss), `fpxMobiliteTID`.

Success: `fpx_debitAuthCode` = `00` and string `Approved`. This post is unauthenticated; display only. Settle from IPN plus status.

### FPX IPN

Default: `GET <merchant_ipn_url>?callBack=<URL-encoded JSON>`. JSON fields: `fpx_msgType` (`AC`), `fpx_msgToken`, `fpx_fpxTxnId`, `fpx_sellerExOrderNo`, `fpx_fpxTxnTime`, `fpx_sellerTxnTime`, `fpx_sellerOrderNo`, `fpx_sellerId`, `fpx_txnCurrency`, `fpx_txnAmount`, `fpx_checkSum`, `fpx_buyerName`, `fpx_buyerBankId`, `fpx_buyerBankBranch`, `fpx_buyerId`, `fpx_makerName`, `fpx_buyerIban`, `fpx_debitAuthCode`, `fpx_debitAuthNo`, `fpx_creditAuthCode`, `fpx_creditAuthNo`, `as_sfid`, `as_fid`, `fpx_debitAuthCodeString`, `fpx_creditAuthCodeString`, `bankName`, `tid`, `mobiLink`, `redirectUrl`, `date`, `time`, `merchantName`, `fpxMobiliteTID`, `service` (`FPX_CALLBACK`), `subMID`.

Optional POST format (on request): `transaction_date`, `transaction_amount`, `transaction_id`, `transaction_order`, `transaction_exorder`, `transaction_description` (`Approved`), `transaction_buyer`, `transaction_bank`, `transaction_code` (`00`), `transaction_callBack`, `transaction_type` (`FPX`), `transaction_signature`.

```text
transaction_signature = base64(3DES_ECB(
  transaction_id|transaction_order|transaction_date|transaction_amount|transaction_description|transaction_type))
```

Verify by decrypting (or re-encrypting the joined fields) with the 3DES key and comparing. The GET format's `fpx_checkSum` verification method is not documented in official docs (checked 2026-10-21); confirm through the status API.

Acknowledge with HTTP 200 and `{"responseCode":200,"responseMessage":"Successful"}`. The IPN URL is static, set at onboarding or in the portal. Retry policy conflicts in the docs ("no automatic retries" and "up to 3 retries"); assume an IPN can be missed or repeated.

### FPX status

`POST /payment/mobiapr19/mobi_jsonservice`, no headers.

```json
{"service":"EXTERNAL_TXN_HISTORY","motoApiKey":"<MOBI_API_KEY>","loginId":"<MOBI_LOGIN_ID>","trxType":"FPX","searchKey":"<sellerOrderNo>"}
```

Response `responseData.forSettlement`: `trxId`, `mid`, `tid`, `status` (`SETTLED`, `PENDING`, `FAILED`), `date`, `time`, `stan`, `rrn`, `latitude`, `longitude`, `amount` (12-digit sen, `000000000100` = RM1.00), `invoiceId`, `txnId`, `txnType`, `hostType`, `aidResponse`. `0000 SUCCESS` with a status, or `0001 FAILURE` "No records found".

## Status Model (normalise locally)

| Local | Mobi values |
|---|---|
| paid | FPX `SETTLED` / debitAuthCode `00`; cards `responseCode 0000`; Boost `completed`; Grab `SUCCESSFUL`/`success`; DuitNow/cash `SUCCESS`; payout `Paid` |
| pending | `PENDING`, `09`, `99`, Boost 0001 "Transaction not completed with QRCode", payout `On Process`/`Pending` |
| failed | `FAILED`, any other FPX code, Grab `FAILED`/`CANCEL`, Boost "Transaction Failed" |
| reversed | Boost `completed-void`, `completed-refund` |

## Amount Formats

- Decimal MYR string or number: checkout, FPX deposit, DuitNow (`"100.00"`), cash, payout (`"10.00"` minimum), Grab callback.
- 12-digit sen string: Boost, Grab init, ShopeePay, TNG, card `carddetails` amount, saved card, FPX status response, Shopee/TNG IPN.
- DuitNow payment sample shows `"amount": "12500"` while the status sample shows `"100.00"` and validation says "Only two decimals allowed"; send decimal and confirm in sandbox.

## IPN Handling Rules

1. Accept only HTTPS; whitelist Mobi IPN IPs from `csmobi@gomobi.io`.
2. Decrypt or verify before parsing business fields.
3. Match order id/invoiceId, amount (right unit), currency MYR, sub-merchant, status.
4. Store the raw event; dedupe on Mobi transaction id.
5. Return HTTP 200 fast (Grab: within 3 seconds).
6. Requery status for anything still pending 5 to 10 minutes after expiry. Mobi cannot resend callbacks manually.

## Errors

Generic: `0000` Success, `0001` Failure, plus standard HTTP status codes (`error-codes`). Product codes and messages: `gomobi-codes.md`.

## Known Doc Conflicts

1. Card encryption: page says RSA/PKCS1, sample is AES-CBC with key and initVector.
2. FPX Python encrypt returns uppercase hex if input contains `#`.
3. Sample form hosts (`services.gomobi.io`, `san.gomobi.io`) differ from stated URLs.
4. Boost/Grab/Shopee/TNG POST IPN `transaction_signature`: "AES-CBC encrypted hash" of id, description, amount, type; order and separator not documented.
5. GrabPay init `tid` ("from earlier handshake") and `sessionId`: handshake not documented.
6. Checkout body-hash encoding not documented.
7. FPX IPN retries: both "no automatic retries" and "up to 3 retries".
8. DuitNow amount sample `12500` vs decimal rule.
9. EZYCASH invoiceId max 30 vs 20 in a note.
10. 3DES table lists 256-bit and 65,536 iterations.
